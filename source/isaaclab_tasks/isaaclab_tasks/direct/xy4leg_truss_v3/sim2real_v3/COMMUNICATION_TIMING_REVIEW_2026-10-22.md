# V3 通信与推理频率检查（2026-10-22）

当前 `68500` 模型的策略周期是 **40 ms，即 25 Hz**，依据配套训练快照 `sim.dt=0.02`、`decimation=2`。`gait_frequency=0.30 Hz` 是步态相位频率。训练相机 `update_period=0.08s`、`render_interval=4` 对应约 **12.5 Hz 图像更新**，也不是策略推理频率。实机 RealSense 配置为 30 FPS，当前 estimator 随策略执行，最多 25 次/秒；取最新帧可能重复使用一帧。这一感知采样频率差异仍需闭环验证。

本轮排除了 Walk 模型选择和训练改动；未修改模型权重、conda 内的 `on_policy_runner.py` 或电机固件，未增加安全停机动作。

## 已定位并处理的通信问题

| 问题与影响 | 本轮处理 |
| --- | --- |
| 反馈逐电机 `read(8)`，单次缺包等待 5 ms；24 个电机都缺包时一轮约 127 ms，最多约 8 轮/秒 | 常态反馈改用 `in_waiting` 批量读取已有数据，无包不调用 `read()`；默认 200 Hz 轮询四路串口，独立于 25 Hz 策略 |
| 原来每轮每腿只读六包，积压后没有余量追上数据流 | 每次解析队列中的完整包，按 ID 更新，保留每个电机最新数据；不足八字节的尾部留待下次拼接 |
| 缺失一路会拖慢另外三路；大量排队旧包可能被当成新反馈 | 无等待地依次轮询各路；有界批量读取超过 8192 字节时，该腿本次不刷新有效反馈。普通读取期间新到的数据留待下次，避免被误判为溢出 |
| 相机 SDK `wait_for_frames` 位于策略循环，等待时间占用 40 ms 预算 | 独立采集线程拥有 SDK 读取权，策略只读取最新缓存；缓存有本机接收时间和序号，默认超过 250 ms 报错，相机线程错误传到主循环 |
| 重复读取缓存帧会重复低通、把同一帧当成不断更新的数据 | 同一帧序号不重复应用低通，bar 记忆年龄使用缓存帧的本机接收时间 |
| 相机/estimator 执行期间，已经读取的电机和雷达观测变旧 | estimator 完成后再读取本体观测，随后构建 actor 输入 |
| 相对 sleep 叠加处理耗时，三个循环的实际频率不能由配置推断 | 策略、反馈轮询、周期 TX 使用单调时钟的绝对时间表；落后整周期时跳过错过的 tick，并统计迟到和遗漏 |
| 两个独立 25 Hz 时钟造成新动作等待下一次 TX，额外接近 0～40 ms | 默认保留 `periodic` 周期重发；增加可选 `--tx_mode on_update`，用条件变量唤醒发送线程，不重复发送同一发布序号 |
| 只看到 `loop_hz`，无法区分推理、反馈、旧指令重发和串口排队 | 增加实际 Hz、p95/max 延迟、重复 TX、RX/TX 队列、无效 ID 包、radar 无效/倒序包等统计，可写 JSONL；异常退出时也尝试保存末次统计 |
| `/dev/ttyUSB0..3` 重新枚举后可能接错腿 | 新增 `--motor_ports LB LF RB RF`，可传 `/dev/serial/by-id/...`，启动时打印映射；同一设备的重复路径/软链接会在开串口前拒绝 |

启动仍由一个读取者逐电机确认使能应答，完成后才启动常态 RX。保留此前逐电机状态/年龄检查及指令有效期检查。常态 RX 不发送探测或其他电机命令。四路发送仍依次下发 24 条命令，原有每条 0.2 ms 的间隔保留。

`on_update` 没有周期心跳重发：策略变慢时，实际发送频率也会下降。这是显式选项，未改变默认模式或固件超时设置。异常只结束软件发送和关闭资源，没有新增失能、归零、零力矩或保持动作。

## 带宽与延迟判断

按当前每路六电机、每条命令 10 字节、每条反馈 8 字节、25 Hz、115200 baud、8N1 估算，每路 TX 为 1500 B/s（约占 13.0%），RX 为 1200 B/s（约占 10.4%）。这是四个独立串口各自的负载；假设每命令回复一包，未包含其他自动上报。

因此，现有证据首先指向 **阻塞等待、队列和时钟相位**。不能仅凭这些估算确认 USB 转换器、CAN 侧或固件延迟已满足要求。每路六条命令的 UART 线速发送本身约 5.21 ms；Python 写入返回也不代表下位机收到或执行。

原始计数、各窗口指标、源文件 SHA256 及测量条件见 [测量数据](COMMUNICATION_TIMING_EVIDENCE_2026-10-22.json)。

| 测量 | 结果 | 范围 |
| --- | --- | --- |
| 修复前四路全部缺包的一轮 RX | 127.24～127.84 ms，3 次 | 模拟每次串口读超时 5 ms；不代表健康实机只能跑 8 Hz |
| 修复后空串口一轮 RX | 平均约 0.005 ms，p95 约 0.0054 ms，1000 次 | 真实收包函数，模拟空串口；不包含 OS/USB 驱动开销 |
| 真实 `68500` actor，CPU 单线程 | 平均约 0.034 ms，p95 约 0.035 ms，400 次 | 按 checkpoint 恢复 MLP 和 normalizer，80→24，batch=1，预热后测量 |
| 真实 `xmax060` TorchScript estimator，CPU 单线程 | 平均约 0.172 ms，p95 约 0.179 ms，400 次 | 合成 64×64 深度输入；不含 SDK、完整观测构建或 Isaac Sim |
| 实际 `play_real.main()` 定义，模拟 I/O，默认周期发送 | 首个约 2s 窗口 policy 25.01 Hz，missed=0；工作耗时 p95 约 1.20 ms；发布到 TX 开始 p95 约 38.80 ms | 真实模型权重；相机每次读取阻塞 33.3 ms，由新采集线程隔离；串口写入模拟 |
| 同一主循环，`on_update` | 首个窗口 policy 25.01 Hz，missed=0；发布到 TX 开始 p95 约 0.12 ms | 同上，不能据此声称真实电机在 0.12 ms 内执行 |

完整主循环内的 actor p95 约 0.15 ms、深度处理含预处理 p95 约 0.76 ms，四路模拟发送完成 p95 约 6.2～6.3 ms；后者包含原有 24 次间隔，不含 UART 线速时间。同步相机读取已从策略耗时中移出。

本机默认 Torch 使用 24 个 CPU 线程。此前同一诊断中的小样本 actor 平均约 2.47 ms，切到单线程后约 0.061 ms，因此部署默认 `--torch_threads 1`，可显式调整。不同采样轮次、预热和系统负载会影响绝对数值，不能把这里的差值作为固定加速比。

**当前没有可见电机串口，CUDA 不可用，未启动真实相机或完整 Isaac Sim。以上仅验证软件路径和 CPU 时间预算，实际实机频率尚未验收。**

## 部署时怎么测

先测真实感知和 actor，不使能电机：

```bash
python source/isaaclab_tasks/isaaclab_tasks/direct/xy4leg_truss_v3/sim2real_v3/play_real.py \
  --enable_camera --enable_radar --headless --max_steps 500 \
  --print_interval 0 --timing_interval_s 2 \
  --timing_jsonl logs/real_v3/timing_sensors.jsonl
```

已有带电运行命令加以下参数即可记录完整链路，仍保留 `--enable_camera --enable_radar --enable_motors`：

```text
--print_interval 0 --timing_interval_s 2 --timing_jsonl logs/real_v3/timing_motors.jsonl
```

需要评估发布到发送的额外等待时，显式比较 `--tx_mode periodic` 和 `--tx_mode on_update` 两次记录。四路设备名可用 `--motor_ports` 指定，顺序严格是 **LB LF RB RF**；使用真实设备路径，不要照抄占位符。

| 输出/JSON 字段 | 含义及判断 |
| --- | --- |
| `policy` | 完成观测、actor 和命令构建/发布的实测频率，当前目标约 25 Hz |
| `tx` / `tx_new` / `tx_repeat` | 完成一组 24 命令的软件发送频率／其中采用新发布序号的频率／重复次数；不等于下位机执行确认 |
| `rx_poll` | 查询四路串口的轮询频率，默认目标约 200 Hz，不能把它当作反馈数据有 200 Hz |
| `rx_complete` | 24 个电机有效反馈计数最小值的增长率；用于识别最慢/缺反馈电机，不代表同时采集的完整帧或动作 ACK |
| `camera` / `radar` | 采集完成／有效 UDP 包接收频率；未启用的源没有样本 |
| `actor_ms` / `depth_ms` / `cycle_ms` | actor 含输出拷回 CPU／深度预处理和网络／本周期工作耗时；`cycle_ms` 不含末尾诊断打印和 sleep，打印阻塞会反映在随后频率和迟到统计中 |
| `feedback_age_ms` / `camera_age_ms` / `radar_age_ms` | 读取时本机缓存年龄；前者取最老电机。不能代替设备采样到主机的实际端到端延迟 |
| `command_age_ms` | 动作发布到开始串口发送的等待时间；用于衡量独立周期 TX 的相位延迟 |
| `observation_to_tx_ms` | 本体观测读取开始到串口发送开始；不含之前的图像年龄、深度网络时间或观测到达主机之前的延迟 |
| `tx_ms` | 下发整组 24 命令到主机串口写接口所用时间，不是机械响应时间 |
| `rx_backlog_bytes` / `rx_pending_bytes` / `tx_pending_bytes` | 四路 RX 读取前最大排队字节数／读取后剩余字节总数／整组发送后最大的主机 TX 队列；持续增长说明链路在积压 |
| `rx_invalid_frames` / `radar_invalid` / `radar_out_of_order` | 未能对应有效电机 ID 的包／坏 UDP 包／重复倒序 UDP 包计数，细项见 JSON |
| `policy_missed` / `deadline_lateness_ms` | 跳过的整周期次数／计划启动时刻的迟到时间，细项见 JSON |

Hz 从该报告内首事件之后的增量除以首事件至报告时刻的单调时长计算，包含最后事件之后的静默。短窗口和退出等待会造成边界偏差；优先看多个 2s 以上稳定窗口，结合原始 `counts`、`window_s`、p95/max 和 `missed` 判断，不能用两次推理的瞬时输出验收持续频率。`n/a` 表示没有样本。

## 仍需实机/协议证据的部分

- 当前反馈是固定八字节，没有在该 Python 接口中提供帧头、长度校验、CRC、设备时间戳或命令序号。分包已处理；任意丢字节后的可靠重同步、数据实际采样年龄、动作是否执行，不能从该接口保证。无效 ID 计数和逐电机过期检查只能发现其中一部分异常；未猜测新的帧格式。
- USB 转换器缓冲、驱动延迟和四腿实际执行时差尚未测量。反馈本来就可能非同时到达；没有做姿态、关节和图像的时间对齐或状态预测补偿。
- `/dev/serial/by-id` 可由命令行配置，但尚不知道各转换器的真实身份、接线和是否提供唯一序列号；自动身份核验未实现。
- Python 线程和普通 Linux 调度没有硬实时保证。默认周期发送的 0～40 ms 相位等待仍存在；新选项需要结合下位机的既有通信超时要求做实机比较。

53 项回归测试通过：39 项部署/通信检查和原有 14 项 crossing logic 检查，覆盖缺包、半包、积压、无效 ID、串口断开、独立相机采集、陈旧帧、周期调度、更新触发发送、计时日志及主循环异常清理。未进行真实驱动测试。测试复现命令见 [修复记录](SIM2REAL_FIXES_2026-10-22.md)。
